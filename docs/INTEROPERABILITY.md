# TruePad 2 — CLI ⇄ Browser interoperability

The Browser Edition and the operational CLI run the **same frozen protocol**
and reuse the **same `src/core` crypto**. This document states what that buys —
a byte-for-byte-identical store on disk and an identical wire envelope — and
records the interop suite that proves it, `tests/browser-interop.test.ts`.

The short version: **a pad pair generated in the browser opens in the actual
`truepad2` CLI, and a pad pair generated by the CLI opens in the browser
engine, with the exact plaintext and the same typed refusals** — not by a
compatibility shim, but because both write the same bytes.

---

## 1. A browser store *is* a FORMAT-V2 store

The browser engine runs its store over the `Vfs` abstraction
(`src/browser/engine/vfs.ts`); in production that is OPFS, in the interop suite
it is a Node-fs `Vfs` (`tests/helpers/node-vfs.ts`, test-only — the one place
`node:fs` is touched, so the `src/browser` core-only layering invariant is
untouched). Either backing writes the **same three files per direction**, the
FORMAT-V2 §1 store:

```
<pair>/a-to-b/head.json     non-secret header (§1.1), compact canonical JSON
<pair>/a-to-b/secret.bin     E + 32·N bytes: [encryption slice][K‖R per record]
<pair>/a-to-b/journal.log     append-only, one JSON line per event (§12.1)
<pair>/b-to-a/…               the reverse direction, same shape
```

The only layout difference is the **root**: the browser roots each pair under a
`<pairId>/` subdirectory (so one origin can hold many pairs), while the CLI's
pair directory *is* that subdirectory. So the CLI operates on
`<root>/<pairId>`, and a browser export bundle / a `cp` of that subtree is a
CLI pair directory verbatim. Extra files the browser keeps at the pair root
(`pair.json`) or the CLI keeps (`manifest.json`) are ignored by the other side;
neither is pad-derived (N14).

### head.json is byte-identical

Both `src/browser/engine/store.ts` and `src/cli/v2/store2.ts` construct the
header in the **same canonical key order** and serialise it with the same
compact `JSON.stringify(head)` — no indentation, no trailing newline. The
interop suite asserts the on-disk bytes directly:

```
{"formatVersion":2,"pairId":"…","direction":"A->B",…,
 "rollback":{"witnessClass":"none","config":{}},…}
```

The one place the browser's vocabulary is richer than the CLI's is the rollback
class. The browser's honest classes are `browser-none` and
`browser-independent-store` (`BROWSER-SECURITY.md` §4). **`browser-none`
serialises to the CLI's `{ "witnessClass": "none", "config": {} }`
byte-for-byte**, so a browser-none store is CLI-readable with no translation.
`browser-independent-store` is a browser-only class the CLI does not honour, so
interop is scoped to browser-none stores — stated, not hidden.

### canonical bytes and the tag are the frozen construction

Tags are computed over the §6.1 canonical bytes by `wc-one-time-v1`, reused
from `src/core` on both sides. The interop suite reproduces the frozen
FORMAT-V2 §11 full-tag vector through the **browser build's** `canonicalBytes`,
`wcHash`, and `wcTag`:

- `wcHash` → `4ba90e0dd06af1497c869bc334117ac6`
- `wcTag`  → `5bb81c1ec47fe75e649f81d8280c64d9`

Because the tag is a deterministic function of the pad's `(K, R)` and the
canonical fields, and both editions read the same `secret.bin` and build the
same canonical bytes, **the same message over the same store yields a
byte-identical envelope from either side** — the suite asserts string equality
of the two wire lines.

---

## 2. The byte-for-byte guarantee, stated precisely

- **PROTOCOL.** The store files, the canonical bytes, POLYVAL, the envelope
  grammar, the four-slice partition, and the fixed-record frame are identical
  on both editions because `src/core` is reused byte-for-byte. A browser store
  and a CLI store of the same budgets, witnessClass `none`, and record policy
  are the **same bytes** but for the random `pairId`, the operator's source
  declarations, and each side's own journal timestamps.
- **Scope.** Interop is proven for **browser-none** stores (the CLI does not
  implement the browser-only witness class). Both editions honour the same
  typed refusals (`FORMAT-V2.md` §14.1), so a hostile envelope is refused the
  same way on both.
- **Not claimed by interop.** Interop is about *bytes and behaviour*, not about
  durability substrate. It does **not** transfer the CLI's native power-loss
  claim to the browser, nor the browser's OPFS story to the CLI — those are the
  per-edition operational claims in `PRODUCT-CLAIMS.md` and
  `BROWSER-SECURITY.md`.

## 3. Interop test results

`tests/browser-interop.test.ts` drives the **real** browser engine
(`src/browser/engine/verbs.ts`) over the Node-fs `Vfs` and the **real** CLI
binary (`spawnSync bin/truepad2.mjs`). It is green: **14 tests passing**.

### Round trips that opened byte-for-byte

| Direction | What was proven |
| --- | --- |
| **Browser → CLI** | The CLI `status` reads a browser-generated store (meters agree). A browser-burned envelope opens in the CLI `open` with the **exact** plaintext (no trailing newline, §12.3 O6). The CLI sees the browser's counter advance; the burner's own copy self-retires, so a replay is refused `sequence-retired`. |
| **CLI → Browser** | The browser engine `status` reads a CLI-generated store. A CLI-burned envelope opens in the browser engine `open` with the **exact** plaintext, and the browser's counter advances to `nextSequence 1`. |
| **Envelope byte-identity** | Burning the *same* message over two byte-identical pre-burn copies — one in the browser engine, one in the CLI — produces the **same wire line, tag included** (asserted with string equality). |
| **Frozen §11 vectors** | The browser build's `canonicalBytes` / `wcHash` / `wcTag` reproduce the frozen FORMAT-V2 §11 full-tag vector. |

The courier model is honoured throughout: a pre-burn copy is couriered to the
receiver *before* the sender burns, exactly as two peers would exchange the pad
out of band.

### Adversarial corpus — the SAME typed refusal from both engines

Each hostile input is run against a **fresh copy** of the base store for each
engine (a mutating refusal such as `auth-failed` reserves a durable attempt, so
copies are never shared across cases). For every case the browser engine's
`reason` and the CLI's `refused: <type>` are **equal** and equal the expected
type:

| Fixture | Both engines refuse |
| --- | --- |
| duplicate key (`"sequence"` twice) | `malformed-envelope` |
| unicode-escaped key (`"pairId"`) | `malformed-envelope` |
| wrong pair id | `wrong-pair` |
| wrong direction (`B->A` opened as B) | `wrong-direction` |
| flipped tag | `auth-failed` |
| replay (open once, then again) | `sequence-retired` |
| oversize (`ciphertextLength` 1,048,577) | `oversize-ciphertext` |
| v1 envelope (`label`, no `formatVersion`) | `envelope-v1` |
| fixed store, wrong ciphertext length | `record-size-mismatch` |
| `maxAuthLookahead 2`, sequence 5 | `sequence-out-of-window` |

The structural refusals (`malformed-envelope`, `envelope-v1`,
`oversize-ciphertext`) come from the shared `decodeEnvelope2` grammar; the
routing, window, size, and authentication refusals come from the two engines'
verbs, which use the identical typed-reason strings.

## 4. Reproducing the interop suite

```
npx tsc -p tsconfig.tests.json      # type-check (browser engine + tests + e2e)
npx vitest run tests/browser-interop.test.ts
```

The suite needs a Node runtime that can run the CLI launcher
(`bin/truepad2.mjs`, Node ≥ 22.18 for type stripping) and writes only to a
temporary directory it cleans up. No OPFS is required — the Node-fs `Vfs` stands
in for OPFS at the same `Vfs` seam the product uses, which is exactly why the
proof carries over to the shipped OPFS backing.
