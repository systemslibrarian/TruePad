# Android 3.0 delta audit — classifying what the `android-phase-2` merge brought, and what the 3.0 port added

> ## SUPERSEDED IN PART — READ THIS FIRST
>
> **This is a HISTORICAL audit record of the `android-phase-2` merge, not current
> product guidance.** It was written when Android had no Sealed Pad Transfer, no
> TPR2 QR and no PQC dependency, and it correctly recorded those as deferred *at
> that time*. All three shipped afterwards.
>
> What changed after this audit was written:
>
> | This document says | Current tree |
> | --- | --- |
> | SPT deliberately not on Android; "do not bolt on a Kotlin PQC stack" | SPT ships — `android/truepad-spt`, X-Wing via **Bouncy Castle** |
> | Native TPR2 QR deferred | Ships — `Qr.kt` encodes, `QrScan.kt` scans via **ML Kit** |
> | Native iOS a separate later task | Ships — `ios/TruePadApp`, physically installed and validated |
> | Physical-handset gate not yet performed | **DONE** — Samsung SM-A176U, plus a two-device ceremony against a physical iPhone 12 |
>
> **The instruction "do not bolt on a Kotlin PQC stack" was scoped to that
> snapshot and is NOT a current requirement.** The stack it warned against was
> subsequently designed, reviewed, tested against cross-edition vectors, and
> physically proven between two handsets.
>
> For the CURRENT Android claims boundary, read `docs/ANDROID-SECURITY.md`. Where
> the two differ, that document is authoritative and this one is history.

**What this is.** A reviewer-facing classification of the entire delta the
`android-phase-2` branch introduced to `master`, sorted by the *kind* of work each
part needs to be trustworthy on TruePad 3.0. It exists because the Android client
was built against an ancestor of the released v2.0.0 wire and therefore predated
the whole 3.0 assurance line; this document separates the parts that are already
current (and need only proof) from the one net-new semantic port, and from the
work still honestly deferred.

**Master SHA this describes:** the 3.0 Android integration on `master`
(`3.0.0-dev.0`) — the merge `1d0ef13`, the evaluator port `1867dc9`, and the
hardening commit `aad47c2` (claims guards + the hostile-mutation matrix) that
follows it. Later commits add the interop-vector re-pin, the QR disposition, and
this audit itself.

**Integration method.** History-preserving, not an `ours`-merge pretending to
carry content. `android-phase-2` (tip `099f5b3`) branched from `2908d58`, an
*ancestor* of the `v2.0.0` tag (`240d7f0`), so its engine is a byte-exact Kotlin
twin of the v2.0.0 OTP / Wegman–Carter / Store-Format-v2 wire. Master's own
message/store wire is byte-identical to v2.0.0 (see `docs/SECURITY-REVIEW-MAP.md`,
`docs/TRUEPAD-3-WHITEPAPER.md`), so the Android wire already matches *current*
master. The real merge commit `1d0ef13` brought the 85-file `android/` tree plus
two additive files (`.github/workflows/android.yml`, `docs/ANDROID-SECURITY.md`)
with no textual conflict (`android/` did not exist on master). The 3.0 *semantics*
were then added on top in an ordinary commit, `1867dc9` (this HEAD): the
deployment evaluator, honest Android fact assembly, a cross-language conformance
corpus, engine surfacing, and a UI row. Nothing below claims the merge itself
ported 3.0 content; the merge brought a v2-era client, and one subsequent commit
made it 3.0-honest.

> The categories are about the *nature of the assurance*, not code size. A file
> can be in A (already correct, prove it) or in C (newly written, test it) but not
> both. Read `docs/ANDROID-SECURITY.md` alongside this — it is the client's own
> security document and it **predates the 3.0 port**, so where it is silent on the
> deployment evaluator this audit is the newer record.

## A — Byte-exact wire twins, ALREADY CURRENT (prove, do not port)

`truepad-core/*` and the Store-Format-v2 serializer in `truepad-storage` are a
literal Kotlin transcription of the released wire. Nothing here is a 3.0 change;
the only 3.0 obligation is to *prove* — not assume — that the twin still
reproduces master HEAD byte-for-byte.

| Item | State on arrival | 3.0 port action | Evidence / tests |
| --- | --- | --- | --- |
| OTP combiner, WC (`wc-one-time-v1`, POLYVAL/GF(2¹²⁸)), §7 partition, Envelope v2, TP2 compact transport, strict JSON reader (`truepad-core/*`, e.g. `Frame.kt`) | Byte-exact v2.0.0 twin | None (no code port); regenerate & verify golden vectors against master HEAD | `CoreVectorsTest`, `SharedVectorsTest`, `ReleasedCorpusTest`, `CompactEnvelopeTest`, `EnvelopeGrammarTest` |

| Interop fixtures `android/vectors/*` generated by the *released* v2.0.0 TS | Present, committed | Re-run `android/tools/regenerate-vectors.sh --check` at this SHA to confirm no drift | `EngineTraceTest` + the `--check` gate |

## B — Storage / state discipline, CURRENT ("LOSS IS ACCEPTABLE, REUSE IS NOT")

The transaction engine is a twin of the browser verbs and holds the same two
orderings. This is current and correct; the obligation is to confirm it via the
lifecycle/reuse suites, not to change it.

| Item | State on arrival | 3.0 port action | Evidence / tests |
| --- | --- | --- | --- |
| BURN-BEFORE-OUTPUT (`Verbs.kt` `burn` S2 durable commit → S3 emit) | Correct | Confirm only | `CrashAndLifecycleTest`, `ReusePreventionTest` |
| Attempt reservation before verify (`open` O3 `reserveAttempt` → O4 verify) | Correct | Confirm only | `ReusePreventionTest`, `CrashAndLifecycleTest` |
| Durable writes (`Store.kt` `commitAdvance`: temp → fsync → `ATOMIC_MOVE` → dir fsync, over `NioFs`) | Correct (Android sense of durable; not power-loss — see ANDROID-SECURITY §2) | Confirm only | `CrashAndLifecycleTest`, `StoreFormatTest` |
| Per-pair exclusive lock (`fs.withLock(pairId)`, in-proc + OS lock, bounded 10 s) | Correct | Confirm only | `ReusePreventionTest`, `CrashAndLifecycleTest` |

| Android-local rollback witness (`Witness.kt`; append-only, leading-newline framed; `noBackupFilesDir`) | Correct; a genuine but restorable-with-the-pair separate-state-file | Confirm only | `WitnessTest` (incl. the weak in-domain config) |

## C — MISSING 3.0 concepts: the NET-NEW SEMANTIC PORT (the core of this work)

The whole 3.0 assurance line was absent from `android-phase-2`. This is the one
category that is genuinely new code, added in `1867dc9`. Android **assembles its
own reality onto the FROZEN evaluator enums and calls the single authority** — it
invents no eligibility rule — and by construction it can **never reach
CONDITIONALLY ELIGIBLE**: an Android device has no TPM-anchored platform authority
and no operator-pinned root of trust, so `assuranceAuthority` is *always*
`unavailable` and `rollback` is *never* `platform-monotonic`.

| Item | State on arrival | 3.0 port action | Evidence / tests |
| --- | --- | --- | --- |
| The single deployment evaluator | Absent | Added `core/Deployment.kt` — a byte-exact **decision** twin of `src/claims/shannon-deployment.ts` `assessDeployment`; same enums, same load-bearing ordering, same three verdicts | `DeploymentCorpusTest.kotlinReproducesTheCanonicalClassificationForEveryCase` |
| Cross-language conformance corpus | Absent | Added `android/vectors/deployment-evaluator-v3.json` (derived from the canonical TS by `scripts/gen-evaluator-corpus.ts`; 56 cases at this SHA) | `DeploymentCorpusTest` (`theCorpusIsNonTrivialAndSelfDescribing`, `noAndroidTupleIsEverConditionallyEligible`, `theTwoAndroidSourceOutcomesAreExactlyAsMandated`) |
| Honest Android fact assembly | Absent | Added `storage/DeploymentAssembly.kt` — storage `native`; assurance `unavailable`; rollback `separate-state-file`(health)/`none`, never `platform-monotonic`; source derived from how the pad was made | `DeploymentAssemblyTest` (all 10 cases) |
| Engine surfacing (derived, never stored) | Absent | `Verbs.kt` `DirectionMeters.deployment`/`sourceClass`, recomputed under the pair lock on every summary | `DeploymentAssemblyTest.aDeviceGeneratedPadIsNotEligible…`, `…anExternalSourcePadIsInsufficientNeverEligible`, `…theWitnessKindNeverRaisesTheVerdictAboveInsufficient` |
| UI assessment row | Absent | `ui/Screens.kt` `DetailsScreen` shows `Assessment` + `Source` + the known reason + the unproven premises, and states plainly an Android pad is never the maximum-assurance profile (`Claims.DEPLOYMENT_CONTEXT`) | `AppSourceAuditTest` (claims discipline); UI covered by `UiJourneyTest` |

**The two mandated Android outcomes** (proven both in the pure evaluator and end to
end through a real `gen`/`import`/`status`): an all-device-CSPRNG pad is a hard
**NOT ELIGIBLE**; an external-declared native pad is **INSUFFICIENT EVIDENCE**. A
regressed or inconsistent witness is a *positive* disqualifier (NOT ELIGIBLE).

## D — Honesty / claims surface

`app/Claims.kt` is the released v2.0.0 `source-claims.ts` text carried over
verbatim, with the only edits being Android API substitutions (e.g.
`java.security.SecureRandom` where the browser named `crypto.getRandomValues`).
The port added one new load-bearing constant, `DEPLOYMENT_CONTEXT`, which *denies*
the strong claim rather than asserting it.

| Item | State on arrival | 3.0 port action | Evidence / tests |
| --- | --- | --- | --- |
| Verbatim source-claims with Android substitutions | Present | Keep verbatim; add the honest deployment-context claim (`DEPLOYMENT_CONTEXT`, `DEPLOYMENT_UNPROVEN_HEADING`) | `AppSourceAuditTest.noClaimAssertsWhatTheProductRefusesToClaim` (sentence-scoped, negation-aware) |
| Forbidden-vocabulary guard on the randomness path | v2 guard present (bans "verified/certified/proven/…", "truly random", etc.) | **Extended for 3.0 overclaims** — the banned list now also bars "maximum assurance", "maximum security", "gold(-)standard", "perfect secrecy", "verified random", "certified entropy" as *positive* assertions | `AppSourceAuditTest.noClaimAssertsWhatTheProductRefusesToClaim` (committed in `aad47c2`) |
| No persisted verdict; no pad-derived fingerprint | Holds structurally (the assessment is derived, never serialized) | **Explicit machine guards added**, mirroring the TS side (whitepaper §15/§18): no self-certifying verdict identifier, no serialized verdict in either stored format, no pad-derived fingerprint, and the UI never hard-codes a stronger label than the evaluator | `AppSourceAuditTest.noSelfCertifyingVerdictIdentifierExistsInShippedCode`, `…theStoredFormatsSerializeNoDeploymentVerdict`, `…noPadDerivedFingerprintIsComputedOrPersisted`, `…theUiNeverHardCodesAStrongerAssessmentThanTheEvaluatorProduces` (committed in `aad47c2`) |

## What is NOT done in software

The engine, storage, hardening, and the 3.0 evaluator are exercised by JVM and
emulator suites. Two kinds of evidence remain outstanding and **cannot be
manufactured in software** (ANDROID-SECURITY §10, whitepaper §20):

- **Physical-device validation** — `android/tools/physical-device-check.sh` is the
  gate and refuses to run against an emulator. Not yet run.
- **Human TalkBack pass** — `AccessibilityTest`/`LargeFontTest` are a baseline, not
  a verdict. Not yet performed.

And **SPT and native iOS were deferred by design at the time of this audit**, not
merely unfinished — both have since been built and shipped; see the supersession
note at the top. No line
of this audit asserts a physical premise: an Android pad's strongest possible
verdict is INSUFFICIENT EVIDENCE, and that ceiling is derived from the platform,
never hard-coded as "insecure".
